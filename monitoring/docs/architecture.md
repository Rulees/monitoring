##
# Управление Мониторингом (Monitoring as Code)
##

Этот репозиторий реализует концепцию Observability-as-Code, интегрируясь в общую GitOps-архитектуру проекта. Мы отказались от разделения по инструментам (Tool-Centric) в пользу разделения по сервисам (Domain-Centric) и строгого конвейера данных.


##
# 1. Как было раньше (Tool-Centric)
##

Исторически файлы группировались по типу инструмента. Все дашборды лежали в одной папке Графаны, а вся математика и алерты Прометеуса — в монолитном файле. Базовые конфиги серверов лежали свалкой в корне.

monitoring/ (OLD)
├── grafana/
│   └── dashboards/
│       └── main/
│           ├── cpu_mem_disk.json                            <-- Свалка всех JSON дашбордов
│           ├── nodes_per_service.json
│           ├── service_telegrambot.json
│           └── services.json
├── rules.yml                                                <-- Единый файл на 1000+ строк для ВСЕХ алертов
├── playbook.yml
└── prometheus.yml

Минусы старого подхода: Потеря визуальной связи между графиком в UI и формулой в бекенде; невозможность масштабирования; нарушение принципов Path-as-Metadata.


##
# 2. Как стало теперь (Data Flow + App Layer)
##

Структура мониторинга теперь разделена на две чёткие зоны: 
1. Инфраструктурный движок (отсортированный по потоку данных)
2. Бизнес-логику (изолированные проекты).

monitoring/

##
# 3. Как добавить мониторинг в свой проект (Инструкция)
##

Мы используем принцип полной изоляции (Share Nothing). Чтобы настроить мониторинг для своего сервиса, не нужно писать конфигурации с нуля.

1. **Найдите эталон:** Проверьте доступные заготовки в справочнике `_examples/`.
2. **Скопируйте в свой проект:** Используйте команду `cp -r` для копирования папки. Например, добавляем Nginx в проект asepta:
   `cp -r _examples/nginx projects/asepta/nginx`
3. **Настройте под себя:** Теперь файлы в `projects/asepta/nginx/` полностью принадлежат вам. Вы можете безопасно менять пороги алертов или графики, не боясь сломать соседние проекты.


##
# 4. Архитектурные Принципы (Best Practices)
##

    Data Flow Pipeline (Визуальный конвейер):
    Базовые конфигурации серверов изолированы от бизнес-логики и пронумерованы (10 -> 40). Дерево папок читается как архитектурная схема потока данных: от их генерации экспортерами до визуализации в Графане.

    Mirrored Paths (Симметрия):
    Путь к файлу мониторинга строго соответствует пути деплоя. Правила для сервиса X всегда лежат в /services/X/. Пайплайн обладает "контекстной осведомленностью" и сам знает, откуда брать дашборды.

    Domain-Driven Rules (Логика важнее инструмента):
    Папка приложения является единым источником истины как для дашбордов, так и для алертов. Файлы .json (Grafana) и .yml (Prometheus) лежат в одной папке. Если разработчику нужно изменить дашборд сервиса и поправить для него формулу алерта, он делает это в одном месте.

    Scalability by "Copy-Paste":
    Для добавления мониторинга достаточно скопировать эталон из `_examples/` в свой проект. Имена файлов (alerts.yml, dashboard.json) остаются неизменными (DRY).

    Dynamic Target Naming (Автоматическое переименование):
    На уровне Git имена файлов максимально короткие. Во время деплоя пайплайн склеивает путь (Path-as-Metadata) и автоматически переименовывает файлы для серверов в формат <target>.<type>.yml (например, service_nginx.alerts.yml). Это исключает конфликты имен на сервере Prometheus.

    Separation of Concerns (Изоляция слоев):
    Глобальные агрегации (global/dashboards), инфраструктурные алерты (global/alerts) и метаданные (global/metadata) вынесены в отдельные независимые слои. Они не засоряют папки бизнес-приложений и обновляются независимо.


##
# 4. Эволюция и Масштабирование (Future Features)
##

По мере роста проекта заложенная архитектура позволяет легко внедрить следующие улучшения:

    Добавление слоя приложений (App Layer): РЕАЛИЗОВАНО. Логика успешно переведена на уровень изолированных проектов в директории `projects/`.

    Partial Deployment (Точечный деплой): В будущем структура папок позволит реализовать точечный деплой мониторинга. Пайплайн сможет опираться на переменные деплоя и отправлять на сервер только те правила (rules/alerts) и дашборды, которые нужны конкретному обновляемому сервису, а не перезаписывать весь стек целиком.
